# 배포 · 데이터 연동 안내

팀원 공용 문서입니다. 계정 비밀번호는 여기에 적지 마세요.

---

## 1. 구성

```
[GitHub]  ichi7365/ICHI-company-homepage      코드 보관
    │  push 하면 자동 빌드
    ▼
[Cloudflare]  ichi-company-homepage           사이트 호스팅
    │  브라우저에서 직접 호출
    ▼
[Supabase]  ichi-homepage                     DB · 로그인 · 파일저장
```

Next.js 를 **정적 export** 로 빌드해 Cloudflare Pages 에 올립니다.
데이터는 브라우저가 Supabase 를 직접 호출하고, 권한은 DB 의 RLS 정책이 막습니다.

## 2. Cloudflare Pages 설정값

프로젝트 생성 시 아래대로 입력하세요.

| 항목 | 값 |
|---|---|
| Framework preset | `Next.js (Static HTML Export)` |
| Build command | `npm run build` |
| Build output directory | `out` |
| Root directory | 저장소 루트 |
| Node version | `20` 이상 |

**환경변수는 `.env.production` 파일로 관리합니다**

Cloudflare 대시보드의 `Variables and secrets` 는 쓸 수 없습니다.
정적 자산만 서빙하는 Worker 라서 아래 안내가 나옵니다.

> Variables cannot be added to a Worker that only has static assets.

애초에 `NEXT_PUBLIC_` 값은 **빌드 시점에 코드에 박히는** 값이라
실행 시점 변수가 필요하지 않습니다. 저장소의 `.env.production` 에 두면
Cloudflare 빌드와 로컬 빌드가 같은 값을 씁니다.

```
NEXT_PUBLIC_SUPABASE_URL       https://lxjshdoliyssoqivyrqj.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY  (anon key)
NEXT_PUBLIC_SITE_URL           https://ichi-company-homepage.ichi-075.workers.dev
```

⚠️ 이 파일에는 **공개돼도 되는 값만** 넣으세요. `NEXT_PUBLIC_` 값은 브라우저에서
누구나 볼 수 있습니다. anon key 는 공개용이며 실제 보호는 RLS 가 합니다.
**service_role 키는 절대 넣지 마세요.**

개인 개발 환경에서 다른 값을 쓰려면 `.env.local` 을 만드세요 (git 제외).

> Cloudflare 의 **Settings → Build → Build variables and secrets** 에 넣는 방법도
> 있습니다. 값을 코드에서 분리하고 싶으면 그쪽으로 옮기면 됩니다.

## 3. 정적 export 의 제약 ★ 꼭 읽어주세요

이 설정에서는 **`src/app/api/` 라우트가 동작하지 않습니다.** 빈 폴더로 남겨두었습니다.

서버가 필요한 작업은 아래로 처리합니다.

| 하려는 일 | 방법 |
|---|---|
| 목록 조회 · 등록 · 수정 · 삭제 | 브라우저 → Supabase 직접 호출 (RLS 로 보호) |
| 로그인 · 회원가입 | Supabase Auth |
| 메일 발송 (문의 알림) | Supabase Edge Function `notify-inquiry` (작성 완료, 하이웍스 SMTP) |
| ~~SMS 인증~~ | **보류** — 회원가입 인증은 이메일 코드 방식으로 대체 |
| 비밀 API 키가 필요한 작업 | Supabase Edge Function (키를 브라우저에 노출 금지) |

> Next.js 의 API 라우트를 꼭 써야 한다면 Next 15 로 올리고
> `@opennextjs/cloudflare` 어댑터를 붙여야 합니다. 현재 Next 14.2 는 지원되지 않습니다.

## 5. DB 준비

Supabase 대시보드 → SQL Editor 에서 `supabase/schema.sql` 을 실행합니다.

만들어지는 테이블 4개입니다.

| 테이블 | 쓰이는 화면 | 권한 |
|---|---|---|
| `profiles` | 회원가입 · 로그인 · 마이페이지 | 본인 것만 |
| `jobs` | 인재채용 | 조회는 전체, 수정은 관리자 |
| `inquiries` | 문의하기 | 저장은 Edge Function 만, 조회는 관리자 |
| `posts` | 게시판 | 조회는 전체, 수정은 작성자·관리자 |

**관리자 지정** — 가입 후 SQL Editor 에서 실행

```sql
update public.profiles set role = 'admin' where email = 'admin@ichi.kr';
```

## 6. 코드 구조

```
src/lib/
├─ supabase.ts        Supabase 클라이언트
├─ auth.tsx           로그인 상태 · 확인모달 · 토스트
├─ form.ts            폼 검증 공통
└─ repo/              데이터 접근 — 화면은 여기만 호출
   ├─ auth.ts         로그인 · 회원가입 · 회원정보
   ├─ jobs.ts         채용공고 CRUD
   └─ inquiries.ts    문의 접수 (Edge Function 호출)

supabase/functions/
└─ notify-inquiry/    문의 저장 + 알림 메일 (설정은 functions/README.md)

src/types/database.ts  테이블 타입 (schema.sql 과 짝)
supabase/schema.sql    테이블 + RLS 정책
```

**화면은 Supabase 를 직접 부르지 않고 `repo/` 를 거칩니다.**
나중에 저장소를 바꿔도 화면 코드는 그대로 둘 수 있습니다.

`repo/` 함수들은 환경변수가 없으면 자동으로 localStorage 로 동작하므로,
Supabase 준비 전에도 화면 작업을 계속할 수 있습니다.

### ⚠️ Supabase Auth 설정 — 오픈 전 필수 조치

현재 상태와 문제입니다.

| 설정 | 현재 | 문제 |
|---|---|---|
| Confirm email | **켜짐** | 가입 후 확인 메일을 눌러야 로그인됨 |
| 메일 발송 | Supabase 기본 | **시간당 몇 통 제한** — 회원이 몰리면 가입 불가 |

실제 확인된 오류입니다.

```
429  over_email_send_rate_limit  "email rate limit exceeded"
```

Supabase 무료 플랜의 기본 메일 서비스는 테스트용이라 발송량이 매우 적습니다.

**해결 (권장 순서)**

1. **개발·테스트 중** — Authentication → Sign In / Providers → **Confirm email 끄기**
   가입 즉시 로그인됩니다. 메일을 아예 안 보내므로 제한에 걸리지 않습니다.
2. **오픈 전** — Authentication → **SMTP Settings** 에 하이웍스 SMTP 등록
   확인 메일·비밀번호 재설정 메일이 `ichi.kr` 이름으로 나가고 제한도 사라집니다.
   그 뒤 Confirm email 을 다시 켜세요.

코드는 양쪽 모두 대응합니다. 이메일 확인이 켜진 상태로 가입하면 `profiles` 행을
바로 만들 수 없으므로, 가입 정보를 auth 메타데이터에 저장해 두고
**확인 후 첫 로그인 때 `getCurrentProfile()` 이 복원**합니다.

### 참고 — Supabase 가 거부하는 이메일 도메인

`example.com` 같은 예시용 도메인은 가입이 거부됩니다.

```
Email address "test@example.com" is invalid
```

테스트할 때는 실제 도메인(`ichi.kr` 등)을 쓰세요.

**로그인 방식 — 이메일 + 비밀번호로 확정했습니다.**

Supabase Auth 의 기본 방식을 그대로 씁니다. 별도 매핑이 없어서 비밀번호 재설정 등
기본 기능이 전부 정상 동작합니다.

시안에 있던 '아이디' 입력칸은 제거했습니다. 이메일이 곧 계정입니다.

| 화면 | 바뀐 점 |
|---|---|
| 로그인 | `아이디` → `이메일` 입력칸, '아이디 찾기' 링크 제거 |
| 회원가입 | `아이디` 입력칸과 '중복 확인' 버튼 제거 (중복은 가입 시 Supabase 가 판단) |
| 마이페이지 | '아이디' 행 제거 (바로 아래 '이메일' 행과 중복) |

> 이 마크업 수정은 `_design/_build.mjs` 의 `patchLoginMethod()` 에서 처리합니다.
> 시안(`_design/*.dc.html`)은 건드리지 않았으므로, 시안을 다시 받아 재변환해도
> 수정이 그대로 유지됩니다.

관련 함수는 `src/lib/repo/auth.ts` 에 있습니다.

| 함수 | 쓰이는 곳 |
|---|---|
| `signUp()` | 회원가입 |
| `signIn()` / `signOut()` | 로그인 · 로그아웃 |
| `sendPasswordReset()` | 비밀번호 찾기 |
| `getCurrentProfile()` | 로그인 상태 확인 |
| `updateProfile()` | 마이페이지 정보 수정 |
| `changePassword()` | 마이페이지 비밀번호 변경 |
| `withdraw()` | 회원탈퇴 |

**Supabase 이메일 확인(Confirm email) 설정**

| 설정 | 동작 |
|---|---|
| 켬 (권장) | 가입 시 확인 메일 발송. 링크를 눌러야 로그인 가능 |
| 끔 | 가입 즉시 로그인. 테스트 단계에서 편함 |

둘 다 코드가 대응하고 있어 어느 쪽으로 두셔도 됩니다.

**아직 안 된 것** (백엔드2 담당)

- 회원탈퇴 시 `auth.users` 삭제 — service_role 권한이 필요해 Edge Function 필요

| 항목 | 값 |
|---|---|

| Deploy command | `npx wrangler deploy` (프로덕션 브랜치) |

| Root directory | `/` |

> 프로덕션 브랜치가 아닌 곳에 push 하면 `versions upload` 가 실행되어
> 업로드만 되고 사이트에는 반영되지 않습니다. 반영이 안 될 때 여기를 보세요.

**Domains 탭**

| 항목 | 상태 |
|---|---|
| Production workers.dev | 켜짐 |
| Preview workers.dev | 켜짐 |
| Custom domains | **비움 — DNS 작업은 마지막 단계** |

**남은 것**

- Supabase 프로젝트가 일시정지 상태로 보임 (`lxjshdoliyssoqivyrqj` 조회 불가) — 대시보드에서 복구 필요
- Cloudflare 환경변수 미등록 (`NEXT_PUBLIC_SUPABASE_*`) — 현재는 브라우저 저장소로 동작
- Edge Function 미배포

**메일 발송 계정 — 전용 계정 사용 권장**

DNS 는 건드리지 않습니다. SMTP 발송은 계정 로그인만 하므로 MX·SPF 와 무관하며,
`ichi.kr` 의 SPF 에 이미 `include:_spf.hiworks.co.kr` 이 있어 스팸 처리 위험도 낮습니다.

다만 대표 메일(`ichi@ichi.kr`) 대신 전용 계정을 쓰는 편이 안전합니다.

```
SMTP_USER    web@ichi.kr    보내는 계정 (신규 생성)
INQUIRY_TO   ichi@ichi.kr   알림 받는 곳 (기존)
```

- 발송 한도에 걸려도 대표 메일 수발신은 영향 없음
- Edge Function 에 등록하는 비밀번호가 대표 계정 것이 아니게 됨

하이웍스에서 **계정별 '외부 메일 프로그램(SMTP) 사용'** 이 허용돼 있어야 발송됩니다.

## 9. 도메인 (마지막 단계)

`ichi.kr` 은 현재 유호스트에서 운영 중이며 **아직 건드리지 않았습니다.**

전환 시 **MX(하이웍스) · TXT(SPF) 레코드는 절대 변경하지 마세요.** 회사 메일이 끊깁니다.
A / CNAME 레코드만 Cloudflare 쪽으로 바꾸는 방식을 권합니다.
